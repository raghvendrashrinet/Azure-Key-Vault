## Integrating Azure Key Vault with CI/CD Pipelines (GitHub Actions / Azure Pipelines)
Retrieving sensitive operational credentials directly from Azure Key Vault during automated CI/CD pipeline execution.

Instead of hardcoding connection strings, API tokens, or credentials inside pipeline variables, build agents fetch them dynamically at runtime from Azure Key Vault using Service Principals or Managed Identities

Overview of the CI/CD Integration Flow
```
┌─────────────────────────┐               ┌───────────────────────────┐               ┌───────────────────────┐
│   CI/CD Pipeline        │               │   Microsoft Entra ID      │               │   Azure Key Vault     │
│  (GitHub/Azure DevOps)  │               │   (Service Principal/OIDC)│               │                       │
│                         │               │                           │               │  ┌─────────────────┐  │
│  1. Triggers Pipeline   │               │                           │               │  │ Docker Registry │  │
│  2. Authenticates ────► │ ────────────► │ Validates Identity        │               │  │ Connection Str  │  │
│  3. Requests Secrets ───┼───────────────┼─────────────────────────► │ Authenticates │  │ Terraforms Keys │  │
│                         │               │                           │  & Returns    │  │ Ansible Keys    │  │
│  4. Injects as Env Vars │ ◄─────────────┼────────────────────────── │  Secrets ────►│  └─────────────────┘  │
└─────────────────────────┘               └───────────────────────────┘               └───────────────────────┘
```
### Common CI/CD Secrets Managed via Key Vault 
1.`Docker Registry Credentials`: Service connection strings or access tokens used to push/pull container images.

2.`Infrastructure as Code (IaC) Secrets`: Sensitive parameters, state backend storage keys, and cloud credentials for Terraform or OpenTofu.

3.`Configuration & Deployment Keys`: SSH keys, private keys, or vault passwords for Ansible playbooks.

4.`Application API Tokens`: Third-party integration tokens used by build or automation scripts (e.g., Python scripts).

Implementation Approaches
**Approach A: Azure Pipelines (AzureKeyVault@2 Task)**    
In Azure DevOps, you can use the official AzureKeyVault task connected via an Azure Resource Manager (ARM) Service Connection:

```YAML
trigger:
  - main

pool:
  vmImage: 'ubuntu-latest'

steps:
  # 1. Fetch secrets from Key Vault
  - task: AzureKeyVault@2
    inputs:
      azureSubscription: 'MyAzureServiceConnection'
      KeyVaultName: 'AKSDemoKeyVault'
      SecretsFilter: 'DockerRegistryPassword, TerraformStorageKey'
      RunAsPreJob: true

  # 2. Use secrets in downstream pipeline steps
  - script: |
      echo "Logging into Docker Registry..."
      docker login myregistry.azurecr.io -u myuser -p $(DockerRegistryPassword)
    displayName: 'Authenticate with Container Registry'
```
**Approach B: GitHub Actions (azure/login & azure/get-keyvault-secrets)**  
Using OpenID Connect (OIDC) federated credentials, GitHub Actions authenticates passwordlessly to Azure and fetches secrets dynamically:

```YAML
name: CI/CD Pipeline

on:
  push:
    branches: [ "main" ]

permissions:
  id-token: write
  contents: read

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      # 1. Authenticate to Azure via OIDC
      - name: Azure Login
        uses: azure/login@v2
        with:
          client-id: ${{ secrets.AZURE_CLIENT_ID }}
          tenant-id: ${{ secrets.AZURE_TENANT_ID }}
          subscription-id: ${{ secrets.AZURE_SUBSCRIPTION_ID }}

      # 2. Fetch Secrets from Azure Key Vault
      - name: Fetch Secrets from Key Vault
        uses: azure/get-keyvault-secrets@v1
        with:
          keyvault: 'AKSDemoKeyVault'
          secrets: 'DockerRegistryPassword'
        id: keyvault-secrets

      # 3. Reference secret output securely in subsequent steps
      - name: Build and Push Docker Image
        run: |
          echo "${{ steps.keyvault-secrets.outputs.DockerRegistryPassword }}" | docker login myregistry.azurecr.io -u myuser --password-stdin
```
Key Advantages over Pipeline Built-in Secrets
 - Centralized Credential Governance: Secrets are stored in a single secure location rather than duplicated across dozens of repositories or pipeline variable groups [
 - Automated & Enforced Rotation: Whenever operational passwords or connection strings are rotated according to compliance policies (e.g., every 90 days), pipelines automatically fetch the updated value without requiring manual variable updates [
 - Unified Audit Logging: Access logs and authorization checks are consolidated in Azure Key Vault diagnostic settings, providing a clear audit trail of build agent activity [
